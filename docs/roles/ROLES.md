# 角色（被守护者 / 守护者）评估与方案

2026-10-31 · 基于 `release/1.0-integration` 代码

---

## 一、现状评估：注册、登录时的角色为什么不稳定

### 现在的模型

- 每个账号只有一个 `users.role`（`"protected"` 或 `"guardian"`），在注册时选定。
- App 首页、后台服务都按这一个字段分支：`RootView` 选 `ProtectedTabView` / `GuardianTabView`，`AppCoordinator` 按它决定开不开跌倒检测、拉谁的数据。
- 后端大部分接口其实按**关系**（`guardian_links`）鉴权，与 `role` 无关。只有 3 处读 `role`：邀请接受、两个定时检查任务、行程列表。

### 发现的问题

| # | 问题 | 用户看到什么 | 证据 |
|---|---|---|---|
| 1 | **邀请方向由双方账号角色决定**。接受邀请时，后端看两个账号的 `role` 来判断谁是守护者；两人同为被守护者或同为守护者就失败 | 「邀请码无效或已过期」（所有错误都显示这一句） | `invite.ts:124-139` ROLE_MISMATCH；`PostSignupWizardView.swift:660` 吞掉所有错误 |
| 2 | **注册时默认选中「被守护者」**，角色选项放在姓名、生日下面，容易不看就点「完成」 | 女儿注册时没改角色 → 输入妈妈的邀请码失败（问题 1） | `SignupView.swift:33` `selectedRole = .protected_` |
| 3 | **点邀请链接没有任何反应**。深链接设置了 `showInviteAccept = true`，但没有任何界面响应这个值 | 点链接打开 App，停在首页 | `AppCoordinator.swift:578-580`，全工程无其他引用 |
| 4 | **完成首次设置后，再也没有输入邀请码的地方**。只有首次设置向导（守护者那一侧）能输入 | 之后想加家人只能重新装 App | 全工程 `/v1/invite/accept` 只在 `PostSignupWizardView` |
| 5 | **守护者发出的邀请，对方无法接受**。被守护者的设置向导只有「生成邀请码」，没有「输入邀请码」；守护者「邀请其他守护者」时，对方也是守护者 → 问题 1 | 邀请发出去了，永远不会生效 | `PostSignupWizardView.swift:388-411`；`GuardianRecordsView.swift:976, 1199` |
| 6 | **未注册号码登录要收两次验证码**。登录输完验证码发现没注册 → 跳到注册页，又从「输入手机号」开始，再发一次 | 多等一条短信，容易触发 Firebase 频率限制「请求过于频繁」 | `LoginView.swift:602-606`；`SignupView.swift:124-133`（只预填号码） |
| 7 | **切换角色会关掉保护**。设置里「切换为守护者」后：跌倒检测停止、锁屏 SOS 卡片和小组件 SOS 失效、后端不再检查失联和逾期报平安 | 没有任何提示；守护者也不知道对方已经不在保护中 | `AppCoordinator.swift:481, 543, 1020`；`checkinOverdue.ts:28`，`heartbeatCheck.ts:25` 只查 `role == protected` |
| 8 | 每次 token 刷新都会把登录流程重跑一遍（`state` 再次发布 `.loggedIn` → `onLoginComplete()`） | 偶发重复请求、重复权限检查 | `AuthManager.swift:277-280` |

> 问题 1、2、3、4、5 叠加起来，就是「角色不稳定」的主要来源：同一个家庭，按不同顺序注册、用不同方式发邀请，结果不一样。

## 二、方案：一个账号，两种身份

### 原则

1. **身份来自关系，不来自注册时的选择。** 有人守护我 → 我是被守护者；我守护别人 → 我是守护者。两者可以同时成立（例：女儿守护妈妈，同时自己独居，也让哥哥守护她）。
2. **保护永不因为「看哪个界面」而中断。** 只要还有守护者，跌倒检测、位置共享、心跳、SOS 就一直运行。
3. **邀请自己带方向。** 邀请码里写明「邀请人将成为什么」，接受的人自动成为另一方，不再检查账号角色。
4. **停止被守护必须明确、可见。** 只能通过「移除守护者」完成，守护者会收到通知。

### 概念

| 概念 | 含义 | 存在哪 |
|---|---|---|
| 身份 `roles` | 账号当前拥有的身份集合：`protected`、`guardian`，可同时有 | `users.roles`（新增数组）；由关系建立 / 解除时维护 |
| 首页视角 `homeMode` | 打开 App 时先看哪一边。纯界面偏好，不影响保护 | 沿用现在的 `users.role` 字段（兼容旧版本） |
| 关系 | 谁守护谁 | `guardian_links`（不变） |

### 什么时候可以「转换」

| 操作 | 什么时候可以 | 需要谁同意 | 结果 |
|---|---|---|---|
| 切换首页视角 | 同时拥有两种身份时，随时 | 无 | 只换界面。保护照常运行 |
| 被守护者 → 增加「守护者」身份 | 随时 | 被守护的那位家人（接受邀请即同意） | 多一个「我守护的人」视角 |
| 守护者 → 增加「被守护者」身份 | 随时 | 自己（发邀请即同意） | 开始被保护：开启定位、跌倒检测等权限引导 |
| 去掉「被守护者」身份 | 移除最后一位守护者时 | 自己；守护者收到「已停止共享」通知 | 保护停止，首页提示「目前没有人守护你」 |
| 去掉「守护者」身份 | 不再守护任何人时 | 无 | 视角切换器消失 |
| 未成年人（< 18）去掉被守护者身份 | 同上，但需二次确认 | 自己；守护者收到通知 | 同上 |

> 不再提供「切换为守护者 / 被守护者」这种整体切换按钮，因为它会悄悄关掉保护（问题 7）。

## 三、UX 流程

### 1. 首次注册

验证码通过后的资料页，把角色问题改成「你想怎么开始？」，**不预选**：

```
你想怎么开始？
 ○ 让家人守护我          我会分享位置、可以一键求助
 ○ 我来守护家人          查看家人是否平安、接收求助
 ○ 我收到了邀请码        自动按邀请加入
```

- 选「我收到了邀请码」→ 出现输入框（深链接打开时自动填好）。注册完成后立刻接受邀请，身份由邀请决定。
- 不选不能点「完成」。
- 选完后，设置向导最后一步按身份给出「邀请家人」或「输入邀请码」，**两个都提供**（「还有别人要加？」）。

### 2. 未注册号码登录

登录输完验证码 → 后端 404 → 直接进入注册的资料页（复用已验证的验证码），**不再发第二条短信**。

### 3. 接受邀请（任何时候）

入口：点邀请链接、首页「家庭圈」→「输入邀请码」、设置 →「加入家人」。

先确认再接受：

```
妈妈（陈秀兰）邀请你成为她的守护者
你将能看到她的位置和电量，并在她求助时收到提醒。
[ SOS 紧急提醒卡片：允许 / 不允许 ]
[ 接受 ]   [ 不接受 ]
```

错误要说清楚：已过期 / 已被使用 / 不能接受自己的邀请 / 对方方案人数已满（附「告诉对方升级」）/ 网络问题。

### 4. 被守护者也想守护别人（你问的场景）

以妈妈为例：妈妈被女儿守护，现在也想照看自己的母亲（外婆）。

1. 妈妈：设置 →「我也想守护家人」。
2. 两种方式：
   - **外婆已经装了 App**：外婆在她的 App 里生成邀请码 → 妈妈输入。
   - **外婆还没装**：妈妈生成「请你让我守护」的邀请链接 → 发给外婆 → 外婆装好后点链接，看到「陈秀兰想守护你，同意后她能看到你的位置……」→ 外婆确认。外婆的同意是必需的（App Store 对位置共享类功能的要求）。
3. 关系建立后，妈妈首页顶部出现切换器：

```
[ 我 ]  [ 我守护的人 · 1 ]
```

4. 妈妈切到「我守护的人」时：
   - SOS 按钮仍然在右下角（自己的求助永远一键可达）；
   - 跌倒检测、定位共享照常运行；
   - 外婆求助时，无论妈妈在哪个视角都会收到提醒。

### 5. 守护者也想被守护

设置 →「让家人也守护我」→ 生成邀请码 / 链接 → 依次开启位置、运动权限 → 首页出现切换器。

### 6. 停止被守护

只能在「我的守护者」里移除守护者。移除最后一位时弹窗：

```
移除后，没有人会再收到你的求助和位置。
跌倒检测、失联提醒都会停止。
[ 仍然移除 ]  [ 取消 ]
```

守护者收到推送「XX 已停止与你共享位置」。

## 四、要改的地方

### 后端

1. **邀请带方向**：`invites.inviterRole`：`"protected"`（邀请人要被守护）/ `"guardian"`（邀请人要守护对方）。旧邀请没有这个字段时，按创建人当时的 `role` 推断。
2. **接受邀请**：按 `inviterRole` 决定方向，**删除 ROLE_MISMATCH**；给双方的 `roles` 加上对应身份（`arrayUnion`）。接受人如果之前没有任何关系，把他的 `homeMode`（`role` 字段）设为新身份。
3. **新增 `GET /v1/invite/preview?code=`**：返回邀请人名字和方向，给确认页用（只读，不改状态；限流）。
4. **错误码**：`INVITE_EXPIRED` / `INVITE_USED` / `SELF_ACCEPT` / `PLAN_LIMIT` / `NOT_FOUND`，iOS 分别显示。
5. **定时任务**：`checkinOverdue`、`heartbeatCheck` 改为检查「有有效守护关系的人」（`guardian_links` 里的 `protectedPersonId`），不再看 `role`。
6. **行程列表**：始终合并「自己 + 我守护的人」，不看 `role`。
7. **移除守护者**：移除最后一位时，从 `roles` 去掉 `protected`，通知守护者（已有移除接口，补通知和 `roles` 维护）。
8. **`GET /v1/user/me`** 返回 `roles`；`PUT /v1/user/me` 的 `role` 只改首页视角，不影响 `roles`。

### iOS

1. `User.roles: Set<UserRole>`；`AppCoordinator.isProtected` / `isGuardian` 由 `roles` + 本地关系计算。
2. **保护服务按 `isProtected` 启动**，不看当前视角：跌倒检测、锁屏卡片、小组件 SOS、`fetchGuardians`。
3. `RootView`：同时有两种身份时显示顶部切换器；切换只改本地视角并同步 `homeMode`。
4. 设置：删「切换为守护者 / 被守护者」，换成「我也想守护家人」「让家人也守护我」。
5. 新的 `InviteAcceptSheet`：链接、家庭圈、设置三个入口共用；先预览再接受；错误分类显示。
6. 注册资料页：三选一，不预选；邀请码路径。
7. 登录 404 → 注册资料页，复用已验证的验证码（`AuthManager.login` 保存 idToken）。
8. `AuthManager`：token 刷新不再重发 `.loggedIn`。

### 兼容与迁移

- 旧数据不需要一次性迁移：读取时 `roles = data.roles ?? [data.role]`，并根据 `guardian_links` 补齐；首次登录新版时写回。
- 旧版 App 只认 `role`：继续写 `role`（作为首页视角），旧版行为不变。

### 测试

- 后端：任意两人（同为 protected / 同为 guardian / 混合）都能按邀请方向建立关系；旧邀请兼容；`roles` 维护；定时任务覆盖「既是守护者又是被守护者」的人；移除最后一位守护者时的通知。
- iOS：切换视角时跌倒检测、锁屏卡片仍在运行；深链接打开确认页；登录 404 不再发第二条短信；三种注册路径。

| 阶段 | 内容 | 解决问题 |
|---|---|---|
| A（先做，风险低） | 邀请带方向 + 去掉 ROLE_MISMATCH；接受邀请确认页（链接 / 家庭圈 / 设置三个入口）；错误分类；注册不预选；登录 404 不再发第二条短信 | 1–6 |
| B | `roles` 双身份；保护服务按身份运行；视角切换器；设置入口替换；定时任务改按关系 | 7 |
| C | 共同守护者（守护者邀请另一位守护者，需被守护者确认） | 第 5 条的后半 |
